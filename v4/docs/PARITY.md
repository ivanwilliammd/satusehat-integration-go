# Builder parity with the PHP SDK

The Go builders are ports of `satusehat-integration` (PHP), which is treated as the canonical
implementation. A builder counts as *proven* only when a test compares its output, field for field,
against a payload produced by the PHP builder for the same inputs.

## How parity is proven

1. A PHP script builds a payload with `PayloadBuilder<Resource>` using realistic SATUSEHAT data.
2. Its JSON output is stored verbatim as `src/builder/testdata/<resource>_php_golden.json`.
3. `src/builder/<resource>_php_parity_test.go` rebuilds the same payload with the Go builder and
   compares both sides with `reflect.DeepEqual`.

The golden is always generated by PHP, never by Go. A test that compares Go against Go would pass
while both sides are wrong, which is exactly the failure this project exists to avoid: a golden
generated from this port once hid a document link written into the wrong attachment field, and the
mismatch was only visible by inspecting the PHP output.

Run everything with:

```sh
gofmt -w src && go build ./... && go test ./...
```

## R5 namespace (`src/r5/builder`)

`src/r5/builder` is a second *name* for the same builders, not a second implementation. Go has no class
inheritance, so each R5 struct embeds the canonical R4 builder:

```go
type AccountBuilder struct {
	*canon.AccountBuilder
}
```

Every canonical method is promoted unchanged, so switching to R5 is an import change. The layer exists
so that a verified R5 difference has a place to live; until then it must not describe one.

`scripts/generate_r5_builder.py` writes the 141 structs plus `r5_surface_test.go`; `--check` fails when
the layer has drifted from `src/builder`. The test refuses to be cosmetic: it compares each promoted
method signature with the canonical one and fails when a method is missing, extra, or shadowed by a
hand-written override that changed the signature (a Go bug it caught during development, where two
types print identically as `builder.AccountBuilder` while living in different packages). It also compares
`Build()` output JSON for all 141 builders.

To make a resource genuinely diverge: delete the `Code generated` marker from its file, write the
implementation, and drop that pair from the generated test table.

## Proven resources (141 of 141)

Every builder has a golden produced by the PHP builder, and a test that rebuilds the same payload and
compares the two sides. There are 153 golden files under `src/builder/testdata/`: one per builder, plus a
few second files for resources where two shapes needed proving — `Claim` minimal against `Claim` full,
`InsurancePlan` with one type against two, `QuestionnaireResponse` with a status against the default.

A list of 141 names would go stale the first time a resource is added, so this file does not carry one.
`ls src/builder/testdata/*_php_golden.json` is the list, and `grep -c "MatchesPHPPayload" src/builder/*_test.go`
is the count of comparisons.

## Behaviour copied from PHP, including where it departs from the FHIR spec

These are deliberate. Changing any of them without changing the PHP builder first would make the two
SDKs disagree.

- **References.** Some builders take plain ids and prefix them (`Patient/1000000001`), others take a
  full reference and keep it, and `MedicationStatement.SetDerivedFrom` writes the value verbatim.
  `MedicationAdministration` never prefixes. The rules differ per resource because PHP differs.
- **Lists versus objects.** `Encounter.participant.type`, `Organization.type`, `Location.type`,
  `DiagnosticReport.result` and `DocumentReference.type` are written as lists even where FHIR declares
  0..1 or a single object.
- **Nested elements.** PHP addresses some elements with path strings (`collection/quantity`,
  `period/start`, `meta/profile`). The port uses `setPath`/`pushPath` so the JSON is nested rather than
  carrying literal `"a/b"` keys.
- **Empty values.** `Coverage.SetType` always writes `display`, even when empty.
  `Location.SetPosition` writes `position` even when every argument is nil.
  `RelatedPerson.AddRelationship` from a bare code writes `"display": null`.
  These three remain, because FHIR tolerates them and the canonical SDK produces them.
- **Defaults baked in.** `Immunization.SetVaccineCodeFromCode` accepts only the single code the PHP
  allowlist contains (93001282). `RelatedPerson.AddTelecom` defaults `use` to `home`;
  `AddCommunication` defaults `preferred` to `true`; `AddName` from a string forces `use: official`.
- **Validation.** PHP throws `InvalidArgumentException` / `FHIRInvalidPropertyValue`; the Go setters
  record the first error in `Err()` and do not write the element, so a caller can report several
  problems at once. `Bundle` (type) and `Immunization` (status, vaccine code) and `Endpoint` (status)
  follow this pattern.

## Defects found in the canonical PHP SDK (fixed)

1. `PayloadBuilderHealthcareService::addIdentifier()` calls `$this->add(...)`. `Builder` defines only
   `set()` and `push()`, so any call fails with `Call to undefined method`. There is therefore no PHP
   payload to compare identifiers against; the parity golden covers the remaining setters and a
   separate Go test covers the identifier.
2. `PayloadBuilderBundle` and `PayloadBuilderMedicationDispense` format timestamps with `date('c')`,
   which uses the PHP default timezone rather than the offset of the input. The same input produced
   `2026-01-05T11:15:00+08:00` on a host configured for PRC while the input carried `+07:00`.
All four are fixed. The first two were repaired in the canonical SDK and the Go port follows; the
last two were realigned with FHIR R4 at the same time:

- `addIdentifier` now calls `push()` in the 88 builders that had the typo.
- Timestamps keep the offset of the input instead of the server's default timezone.
- `protocolApplied` writes `series` as a CodeableConcept and takes `seriesDosesPositiveInt` as a
  separate optional argument.
- `costToBeneficiary` nests `value` and `currency` inside `valueMoney`.

Anything below that still looks unusual in a payload is therefore a shape FHIR allows, not a defect
carried over.

## Remaining work

The builder surface is complete: 141 builders, 1,403 methods in the canonical SDK, none missing from
the port. Completeness there was measured by reading struct declarations, not filenames — an earlier
count compared snake_cased filenames and reported twenty-five builders as missing when their files were
simply named without underscores.

The proof is complete too: all 141 builders have a payload compared against the PHP builder, in 153 golden
files. A builder whose methods exist but whose payload was never compared is a builder that may be writing
the right value under the wrong key — several did, and the goldens are what found them:

- `InsurancePlan.SetType` replaced the whole element, so a plan with two types kept one.
- `Patient.SetMetaProfile` and `Group.SetMetaProfile` discarded the earlier profile.
- `QuestionnaireResponse` sent no status at all when the caller set none, and accepted statuses FHIR does
  not allow for a response.
- `Task.SetStatus` and `Task.SetIntent` panicked instead of reporting, `AddRestriction` dropped the period,
  and `AddInput` could not take a CodeableConcept.
- `Group.AddMember` read its arguments by position rather than by type, so a caller passing only a period
  lost it silently.
- `ChargeItem.SetEncounter` wrote `encounter` instead of `context`; `PaymentReconciliation.detail.amount`
  wrote a bare number where FHIR wants Money.

The method that finds these is the same every time: call the PHP builder, capture the payload, call the Go
builder the same way, compare.

## Deliberate deviations carried from the canonical SDK

These write elements FHIR R4 does not declare. The port reproduces them because payloads already in
production depend on them, and a change here would be a change to the canonical SDK first:

- `Appointment`, `AppointmentResponse`, `Communication`, `CommunicationRequest`, `DetectedIssue` and
  `Consent` all expose `setEncounter`, writing an `encounter` element. FHIR R4 declares no such element
  on any of the six; the closest is `Appointment.partOf` and `Communication.encounter` — the latter is
  the only one of the six that FHIR actually defines.
- `ExplanationOfBenefit.setUse` writes a CodeableConcept, while FHIR declares `use` as a code.
- `Claim.addRelated` writes a coding into `related.reference`.
- `ClinicalImpression`, `RiskAssessment` and `Device` accept an annotation or a plain string for notes and
  write whichever the caller passed.

Each carries the same comment in the source, so a reader of the builder does not have to find this file.
